## Context

当前架构文档已经规定 React → 类型化 API → Tauri 命令 → 应用服务 → 仓储端口/Provider 的依赖方向，但实现仍处于迁移期。审计基线中 `lib.rs` 约 8,981 行、`workspace.rs` 约 4,825 行、`api.ts` 约 1,640 行；它们通过棘轮预算暂时允许超限，但只能缩小。

当前主线并非简单旧代码：本机运行使用受管源码快照和连续验证，服务器上线通过 `prepare_managed_server_deployment` 复用 deployment-path 执行内核，更新和恢复又共享运行记录、制品、验证与当前指针。重构必须保持这些跨层不变量，并避免创建一套与现有行为并行的新模型。

## Goals / Non-Goals

**Goals:**

- 让 Tauri command 只负责输入边界、状态获取与应用服务委派。
- 让应用服务显式编排来源、环境、部署和验证用例，Provider 与 SQL 不再与命令注册混在同一入口。
- 让前端 Feature 依赖按领域拆分的类型化 API，`api.ts` 只保留可度量的迁移门面。
- 在不修改数据库 schema 的前提下，按聚合和查询职责缩小 `workspace.rs`。
- 保持当前用户行为、错误代码、序列化契约、事务和重启恢复一致。

**Non-Goals:**

- 不重新设计页面、产品对象或部署状态机。
- 不引入新的框架、依赖注入容器、ORM 或数据库。
- 不实现代码仓库 URL 来源。
- 不要求一次性把所有历史 Provider/render/plan 文件重写到理想结构。

## Decisions

### 1. 按产品用例垂直迁移，而不是按函数类型横切

以“来源解析与本机运行”“服务器准备与上线”“部署查询与证据”“更新与恢复”为迁移切片。每个切片同时建立 command、application、workspace 端口及前端 API 入口，完成回归后再迁移下一片。

备选方案是先集中搬完所有 commands、再搬所有 SQL。该方案会长期留下跨新旧模块的半成品依赖，难以验证单步行为，因此不采用。

### 2. 保持 Tauri 命令名与序列化契约稳定

现有生产前端使用的命令名、参数形状、返回结构和稳定错误代码在迁移期间不变。新 command 模块可以包装应用服务，但不要求 React 同时切换协议。只有内部类型不再穿越 Tauri 边界时才允许迁移到领域模块。

### 3. 应用服务通过显式依赖调用仓储与 Provider

应用服务接收 `WorkspaceState` 暴露的窄接口和现有 Provider 能力，负责事务顺序、幂等恢复和错误映射；command 不拼 shell、访问 SQL 或决定 Provider 流程。现阶段使用普通 Rust 结构体与函数参数，不引入 DI 框架。

### 4. Workspace 先拆实现文件，后评估端口抽象

保持 `WorkspaceState` 作为当前 SQLite 聚合入口，通过子模块承载 deployment paths、runs/evidence、connections/config 和 migrations。公开方法可委派到子模块，事务边界和 schema 不变。

备选方案是同步更换 repository trait 与数据模型。它会把纯结构迁移扩大为 schema/领域改造，且不利于证明行为等价，因此留给有明确需求的后续 change。

### 5. 前端 API 使用领域模块并保留单向兼容门面

Feature 新增或迁移的导入直接指向 `api/source`、`api/environments`、`api/deployments`、`api/evidence` 等稳定模块。`api.ts` 可以暂时再导出仍有广泛调用的函数，但不得承载新业务逻辑；每完成一个切片就删除相应再导出。

### 6. 用契约测试和数据不变量证明等价

命令级测试验证参数、返回和错误脱敏；应用服务测试验证编排与失败恢复；Workspace 临时数据库测试验证事务、迁移和当前指针；现有 React 行为测试验证页面不变。文件移动本身不构成完成证据。

## Risks / Trade-offs

- [循环依赖在迁移中暴露] → 以用例切片定义单向依赖，先移动纯类型/窄端口，再移动编排实现。
- [错误文本或序列化字段发生无意变化] → 在命令边界增加契约测试，保留稳定错误代码并比较现有前端归一化结果。
- [Workspace 拆分破坏事务原子性] → 事务仍由同一连接和 `WorkspaceState` 入口管理，先移动实现而不拆跨聚合事务。
- [纯搬移产生大量评审噪音] → 小批量切片，每批包含可验证的行数净缩减、明确入口和回归结果。
- [后续仓库来源仍找不到接入点] → 最终实现索引按用例列出 command/application/repository/provider 起点，并用 CodeGraph 复核。

## Migration Plan

1. 在旧命令面退役完成后的干净基线上重测文件预算和主线调用图。
2. 先建立目录骨架与边界契约测试，不复制实现。
3. 按本机、服务器、查询/证据、更新/恢复顺序逐个迁移垂直切片。
4. 每片迁移后删除原位置实现与前端再导出，运行相关 Rust、React 和 Workspace 测试。
5. 更新实现清单、质量预算和 CodeGraph，最后运行完整门禁。

回滚以切片为单位：若某片无法证明等价，恢复该片到原入口，不影响已完成的其他切片。

## Open Questions

- 深度设计阶段需要根据第一项 change 清理后的实际代码规模确定切片边界和优先级。
- `mvp_environment.rs` 是当前应用服务起点还是过渡适配层，需要在 CodeGraph 调用者复核后决定保留命名或迁入 `application/`。
- Workspace 中少量跨聚合事务应保持集中还是建立内部协调器，需要以现有事务测试为依据决定。
