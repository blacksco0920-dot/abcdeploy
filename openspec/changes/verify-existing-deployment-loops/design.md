## Context

项目当前有三类事实需要严格区分：代码与自动测试证明的 `IMPLEMENTED_UNVERIFIED`、用户在真实桌面客户端明确确认的 `VERIFIED`、以及产品合同要求但尚未接通的 `TARGET`。完整 `pnpm check` 已覆盖 258 个 Rust 测试、195 个前端测试和生产构建，但现有测试分散在 Feature、Tauri、Workspace 与 deploy-core，尚未形成按用户路径组织的闭环证据矩阵。

本地文件夹 → Linux 服务器已有用户验收；本机运行、更新和恢复只有自动证据。前两个 change 会删除旧命令并迁移边界，因此本 change 在稳定结构上补齐跨层测试、测试包和人工验收，而不是用测试数量推导产品状态。

## Goals / Non-Goals

**Goals:**

- 为本机运行、服务器上线、更新和恢复建立按用户路径组织的自动验证矩阵。
- 证明成功来自不可变源码/版本、实际运行、连续健康与用户访问证据，而非命令退出或构建成功。
- 证明失败、重启和恢复场景保留可继续工作的持久化事实。
- 生成当前 macOS Apple Silicon 签名 `.app` 并提供短而可重复的用户验收脚本。
- 只在用户明确验收后更新 `VERIFIED` 状态。

**Non-Goals:**

- 不覆盖代码仓库 URL 来源；它继续是下一轮独立能力。
- 不接触正式版本号、标签、Release、DMG、全平台安装包或官网分发。
- 不要求自动测试访问个人生产账号、真实密钥或长期外部环境。
- 不以本 change 为由重新设计已经稳定的产品交互。

## Decisions

### 1. 以用户路径矩阵组织证据

每条路径都映射来源解析、环境准备、待办门禁、运行任务、成功证据、首页/详情恢复和失败保留行为。测试可以分布在不同层，但验证报告必须把它们关联到同一验收场景并指出仍需人工确认的部分。

备选方案是只运行完整测试套件并记录通过数量。它无法说明哪条用户路径被证明，也会掩盖端到端空白，因此不采用。

### 2. 自动验证使用受控夹具，外部真实性由人工验收补足

本机路径使用真实受管目录、进程/端口或可控替身验证状态转换；服务器路径的 Provider 单测使用匿名化夹具与命令契约，不连接个人账号。最终签名 `.app` 由用户在当前开发机和可用服务器资源上执行真实验收。

### 3. 成功与当前在线版本采用领域事实门禁

本机和服务器均要求来源身份、实际运行身份、必要服务和访问端点证据；关键检查连续通过 3 次、相邻至少 5 秒、总窗口至少 10 秒。更新和恢复只有在验证成功后才移动 `CurrentDeployment` 指针，失败只追加事实。

### 4. 自动通过与用户验收分开落账

OpenSpec/Comet 验证报告记录命令、测试、构建产物和未验证项；`docs/current-state.md` 只有在用户明确反馈真实客户端场景通过后才将对应能力从 `IMPLEMENTED_UNVERIFIED` 升为 `VERIFIED`。已有服务器验收不会因自动重测被重复创造或撤销。

### 5. 发现缺陷时在本 change 内闭环，范围扩张则停止

若现有路径违反产品合同，先增加可复现测试，再修复并重跑矩阵。若修复需要新增仓库来源、改变产品对象、数据库 schema 或引入新 Provider，则视为范围扩张，回到 Comet 决策点而不是悄悄扩大本 change。

## Risks / Trade-offs

- [外部服务器状态不可重复] → 自动层验证 Provider 契约与状态机，真实环境步骤显式记录前置条件、时间和用户结果。
- [人工验收遗漏边界场景] → `.app` 验收脚本只包含少量高价值场景，并由自动测试承担组合与失败分支。
- [测试为了通过而重复实现生产逻辑] → 测试优先调用公开用例/投影与真实临时 Workspace，不在测试中复制状态推导。
- [验证中发现架构 change 遗留缺陷] → 以失败场景先测试后修复；若属于前置 change 的范围，记录关联但不改写历史证据。
- [签名或打包环境失败] → 保留完整门禁结果和构建日志，明确区分代码失败、签名环境失败与用户验收未执行。

## Migration Plan

1. 在前两个 change 归档后的稳定基线上建立用户路径验证矩阵和缺口清单。
2. 按本机、服务器、更新、恢复顺序补齐最小跨层测试；每个缺陷遵循先复现后修复。
3. 运行完整门禁并记录自动验证报告。
4. 运行 `pnpm tauri:build:app` 生成签名 `.app`，核对包身份和启动能力。
5. 提供真实客户端验收脚本，等待用户反馈；只根据明确反馈更新 `docs/current-state.md`。

## Open Questions

- 用户验收时可复用的 Linux 服务器和 Provider 连接状态可能变化，执行前需只读确认环境，不把个人凭据写入测试资产。
- 本机真实验收使用仓库内 `examples/hello-fullstack` 还是用户指定项目，将在 build/verify 阶段根据可重复性决定；两者都不能替代用户对最终体验的判断。
