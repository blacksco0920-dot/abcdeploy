## Why

当前完整自动门禁虽然通过，但除“本地文件夹 → Linux 服务器”正向 MVP 外，本机运行、更新和版本恢复仍只有实现与自动测试证据，没有真实桌面客户端验收；跨层清理和重构完成后也需要重新证明这些路径仍形成同一持久化闭环。若不把自动验证、测试包和用户验收分层记录，项目容易再次把“测试通过”误写成“产品已验收”。

## What Changes

- 为本地文件夹 → 本机运行建立从最终快照、启动、连续验证到重启恢复的跨层闭环测试。
- 复核本地文件夹 → Linux 服务器的部署、运行证据和首页/详情恢复主线，不改变已有用户验收事实。
- 为更新部署建立源码变化、无变化、失败保留在线版本和成功切换新版本的闭环验证。
- 为版本恢复建立历史版本资格、创建新运行记录、失败不切换和成功原子切换的闭环验证。
- 统一记录自动测试证据、真实环境前置条件和用户验收步骤，失败时提供可恢复诊断。
- 运行完整门禁并生成签名的 macOS Apple Silicon `.app` 测试包；只有用户在真实客户端确认后才更新 `current-state.md` 的 `VERIFIED` 状态。

## Capabilities

### New Capabilities

- `deployment-loop-acceptance`: 定义已实现部署路径的跨层验证矩阵、真实客户端验收和状态升级要求。

### Modified Capabilities

无。

## Impact

- 主要影响本机运行、服务器上线、部署列表/详情、更新、恢复及 Workspace/Tauri/React 的测试与验证资产。
- 允许修复验证发现的当前行为缺陷，但任何超出既有产品合同的功能扩张必须回到对应 change 重新设计。
- 需要构建当前 macOS Apple Silicon `.app`；不修改版本号、不生成 DMG、不创建标签、不触发 Release 或全平台构建。
- 代码仓库地址来源继续保持 `TARGET`，不纳入本 change 的闭环或验收。
- 本 change 依赖前两个清理与边界收敛 change，避免在结构仍变化时重复建设跨层证据。
