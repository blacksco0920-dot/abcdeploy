# ABCDeploy 前端设计规范

## 1. 设计原则

ABCDeploy 面向不理解部署概念的用户。页面只帮助用户回答五个问题：

1. 我要运行哪个项目？
2. 项目运行在哪里？
3. 开始前还缺什么？
4. 系统现在正在做什么？
5. 凭什么相信已经成功？

每个界面元素都必须直接服务其中一个问题。不能说明必要性的元素不进入页面。

默认遵循：

- 系统能判断、生成、安装或验证的事情自动完成；
- 只有必须由用户输入、授权、选择或在外部平台完成的事情进入待办；
- 技术实现默认隐藏，需要排障时才按需展开；
- 一个页面只有一个当前主操作；
- 用户可见成功只来自实时证据，不来自按钮点击、旧缓存或阶段数量。

## 2. 视觉基线

采用克制、安静、可信的桌面工具风格。实际桌面端页面与本规范共同构成唯一视觉基线。仍被保留的历史 HTML 原型仅用于追溯，带有非权威提示且从默认导航隔离，不作为并行设计来源；是否删除必须由对应 change 明确决定。

推荐 Token：

| 用途 | 颜色 |
| --- | --- |
| 页面背景 | `#f7f7f6` |
| 内容面 | `#ffffff` |
| 普通边框 | `#e2e2df` |
| 主文字 | `#171717` |
| 主按钮 | `#20201f` |
| 选中强调 | `#0f766e` |
| 成功 | `#18794e` |
| 警告 | `#a45a0a` |
| 错误 | `#b42318` |

- 字体使用 Inter、系统字体和 PingFang SC；
- 页面标题 20px，区域标题 16px，正文和按钮 14px，辅助文字 12px；
- 间距按 4px 倍数，常用 8、12、16、24、32；
- 控件高度 36–40px；
- 普通圆角 6–8px，独立结果面可使用 10–12px；
- 使用 16px Lucide 图标，不混用表情符号充当正式图标；
- 阴影只用于弹窗或必要的浮层，普通内容依靠留白和细边框分组。

优先复用 `components/ui` 中已有的 Button、Input、Dialog 等基础控件和共享 Token。组件库是实现手段，不得改变这里定义的信息架构。

## 3. 页面信息架构

MVP 只有两个核心页面。

### 3.1 我的部署

首页包含：

- 产品标识；
- `我的部署` 标题；
- 唯一主操作 `新建部署`；
- 已保存部署列表。

MVP 不提供搜索。记录数量真正造成查找困难时再增加，不能为了填满首页预放控件。

一条部署记录表示“一个项目来源 + 一个运行位置”。列表行只展示：

- 项目名；
- 运行位置；
- 当前真实结果；
- 可用时的访问地址；
- 最近验证时间；
- 打开详情入口。

项目名默认直接展示本地根文件夹名或去掉 `.git` 后缀的仓库名；不在新建流程增加“项目名称”必填项，也不从项目内容猜测业务名称。用户后续主动重命名时只替换显示文案，不改变部署身份。同名部署允许存在，依靠运行位置和地址区分。

首页只包含本节列出的元素。设置和技术管理能力只能从具体任务或次级入口按需进入。

### 3.2 新建或编辑部署

使用一个自然纵向页面，内容固定按以下顺序排列：

```text
项目来源
运行位置
自动检查与完整待办
唯一主操作 / 运行过程 / 最终结果
```

未选择项目时，运行位置区域保持不可操作并解释原因；项目和运行位置都确定后立即自动检查。修改任一选择后，受影响的待办和证据失效并重新检查。

## 4. 项目来源

只提供两个互斥选项：

- `本地文件夹`：打开系统文件夹选择器；
- `代码仓库地址`：输入或粘贴 Git 仓库 URL。

选择后展示最少确认信息：项目名、路径或仓库地址、分支/快照身份、识别服务数。框架、运行描述、代码平台和扫描过程默认不展示。

仓库输入为空或明显不符合 Git URL 结构时，在输入框旁直接报错，不启用运行位置选择。格式正确后才创建候选对象；私有仓库授权、仓库不可达、无法读取默认分支或内容不可运行等问题进入完整待办列表。MVP 不提供分支选择，固定读取默认分支并展示 Commit SHA。

本地文件夹选择时只形成发现快照。点击运行/上线前重新读取内容；有变化就使旧检查失效并重扫，最终任务只引用新的不可变快照。默认不向源码目录写文件。

## 5. 运行位置

只提供两个互斥选项：

- `这台电脑`；
- `服务器`。

选择服务器后可以从已验证服务器中选择，也可以连接新服务器。首次连接表单由当前适配器的字段声明生成，只展示建立连接确实需要且用户能够提供的信息；协议、默认端口、登录身份和凭据类型不得写死在通用组件中。

名称从验证后的连接事实中生成，连接后可在次级设置中改名。页面只在适配器声明需要用户判断时展示目标身份确认；其他身份、凭据和支持性检查由系统完成。验证通过前不修改服务器，临时凭据在建立可复用连接后立即清除。项目域名、运行工具和项目端口不是连接表单字段。

连接方式不受当前适配器支持时，在写入服务器前明确提示暂不支持。支持矩阵作为检查结果呈现，不变成让小白理解或选择的技术选项。

服务器连接只代表“能管理这台服务器”，不携带项目地址。每个公开服务的访问地址属于具体部署；服务器适配器能够安全提供临时地址时由系统自动准备，用户选择自有域名后才出现相应的解析与安全访问待办。

## 6. 自动检查与待办

项目和运行位置候选确定后，页面原位显示检查状态，完成后一次展示全部阻塞项。整体状态必须可区分：

- `正在检查`：还有必要检查器未结束；
- `需要处理`：检查已结束，存在用户待办；
- `可以开始`：所有必要检查已结束且没有未完成待办；
- `系统准备失败`：系统检查或自动动作自身失败。

只有 `可以开始` 能启用主按钮；不能因为并发检查途中待办暂时为 0 而提前点亮。

待办区域必须包含：

- 准确总数和已完成数量；
- 每一项的名称；
- 为什么需要；
- 当前验证状态；
- 仅在需要用户参与时出现的处理按钮。

状态只有：

- `待处理`；
- `检查中`；
- `已完成`；
- `仍有问题`。

不使用“等待前项”隐藏后续问题；所有已知待办始终可见。系统可以建议处理顺序，但不能迫使用户逐屏发现问题。

用户提交信息后，行进入 `检查中`，只有系统验证通过才变为 `已完成`。不能提供纯粹的“我已完成”自我确认按钮。

系统能完成的动作放在只读的“系统已确认”结果中。自动动作失败显示发生了什么、已保留什么、`重试` 和 `查看技术详情`；不能把系统准备步骤包装成用户待办。

## 7. 主操作

每屏最多一个视觉主按钮：

- 本机：`在本机运行`；
- 服务器：`上线到服务器`；
- 任务中不提供伪操作按钮；页面直接展示进度，并用不可点击的
  `正在运行` / `正在上线` 状态说明任务仍在继续；
- 公网证据不足：`重新检查访问`；
- 成功：`打开项目`。

待办未完成时按钮禁用，并在旁边明确写 `完成 N 项待办后可以运行/上线`。不能只把按钮变灰。

配置、服务器和授权等次要动作使用普通按钮或行内入口，不与主操作竞争。

## 8. 运行过程

用户开始后，页面下半部切换为紧凑进度列表：

```text
读取源码
准备运行版本
启动服务
验证结果
```

每行只展示状态、当前动作和一句结果。平台名、协议、容器、制品摘要、命令和原始日志只在确有帮助的技术详情中出现。

进度头部同时展示 `第 N/M 步`、完成比例、已运行时长和最近活动时间。进度必须来自后台持久化状态；不得在一个长时间阻塞的前端请求上反复显示静态“正在处理”。超过 30 秒没有新活动时，使用中性提示说明正在等待远端，并明确任务可以在关闭客户端后恢复。

`查看部署详情` 可展开任务编号、构建编号、代码版本、制品数量、内部阶段、Provider、脱敏日志和错误码，但该区域只读，不提供节点拖拽、连线或凭据编辑。后台返回终态后，页面必须立即结束加载态并显示真实成功或失败结果。

后台轮询不得抢焦点、改变滚动位置、重新打开已关闭弹窗或重置用户选择。

## 9. 成功结果

成功结果必须先展示用户价值，再展示证据：

1. `运行成功` 或 `上线成功`；
2. 可打开的访问地址；
3. 选择的源码身份；
4. 实际运行位置与实际版本/进程；
5. 必要内部服务和依赖健康；
6. 每个公开服务的本机或公网访问检查；
7. 连续通过次数和最近检查时间；
8. 按需展开的技术详情。

多服务项目要区分内部依赖和公开服务。每个公开服务都有独立地址，并指定一个主地址；首页展示主地址和“另有 N 个地址”，结果区域展示全部地址。只有全部必要内部服务健康、全部公开地址验证通过才算成功。系统无法判断公开服务时，将“选择需要公开的服务”作为用户待办。

本机和服务器使用不同措辞。服务器内部服务已运行但公网失败时，只能显示：

> 服务已运行，访问地址仍需处理

此时保留已经成立的事实，把公网问题放回待办，并提供 `重新检查访问`。不得显示绿色成功，也不得重复构建相同版本。

没有项目声明的健康接口或冒烟检查时，只能证明服务运行和地址可访问，不能宣称登录、支付等业务功能正常。

关键检查连续通过 3 次，相邻至少 5 秒，总窗口至少 10 秒。证据 5 分钟后不再代表当前状态，显示 `上次验证通过 · 待复查`；打开已有部署时自动复查，离线时只展示历史时间，不能保持当前绿色成功。

## 10. 错误与恢复

所有错误固定回答：

1. 发生了什么；
2. 已经完成和保留了什么；
3. 原有运行版本是否仍可用；
4. 用户现在需要处理什么；
5. 处理后系统从哪里继续。

原始 JSON、scope、命令和 Provider 错误码放进技术详情。用户关闭客户端后再次打开，应恢复同一次部署任务，而不是从头猜测。

## 11. 文案规则

- 使用用户目标：项目、这台电脑、服务器、运行、上线、访问地址、待办；
- Provider 名称只在选择授权来源或技术详情中出现；
- 避免“制品、流水线、digest、反向代理、容器编排、阶段投影”等默认文案；
- 配置项标题来自项目注释，没有注释时显示原始 Key，不由 ABCDeploy 猜测业务含义；
- 按钮使用明确动词，不使用含糊的“继续”“确认”“下一步”作为最终主操作。

首版只支持至少包含一个 HTTP 可访问服务的项目。纯 CLI、Worker 或定时任务应在选择项目后明确提示暂不支持，不能进入一个永远无法产生访问证据的部署流程。

## 12. 可访问性与窗口适配

- 图标按钮必须有可读名称和 Tooltip；
- 选择卡、待办操作、弹窗和主按钮可通过键盘完成；
- 状态同时使用文字和图标，不能只依赖颜色；
- 焦点环清晰可见；
- 1280px 桌面窗口无需横向滚动；
- 窄窗口按纵向排列来源、环境和证据，不缩小到无法阅读；
- 长地址、路径和摘要允许换行或中间省略，并能复制完整值。

## 13. 范围纪律

- `我的部署` 和单页部署编辑器是 MVP 唯一一级信息架构；
- 新元素必须直接帮助用户选择项目、选择运行位置、处理待办、执行主操作或判断结果；
- 同一事实只保留一个权威展示和一个明确修改入口；
- 不为填满页面添加统计卡、说明卡或装饰状态；
- 当前代码已经存在的页面或组件不能作为新增界面要素的理由。
