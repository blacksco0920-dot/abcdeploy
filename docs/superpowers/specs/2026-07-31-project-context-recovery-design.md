# ABCDeploy 项目上下文恢复设计

## 1. 目的

本设计把 ABCDeploy 的当前产品事实、稳定产品规则、技术边界、代码证据和变更历史拆分为职责明确的仓库资产，使没有历史聊天上下文的新 AI 会话也能在有限阅读量内准确接手项目。

规范性需求以 `openspec/changes/organize-canonical-project-assets/specs/project-context-recovery/spec.md` 为准；本文只说明实现结构、维护协议和验证方法，不另建一套平行规范。

## 2. 范围与非目标

本次变更只治理文档、上下文恢复入口、变更导航和代码定位说明。它不会：

- 修改部署、回退、版本管理或 Provider 业务行为；
- 清理当前脏工作区中的用户改动；
- 删除历史原型、历史分支或归档变更；
- 升级应用版本、生成 DMG 或触发正式发布；
- 将尚未验证的功能包装成可推广能力。

## 3. 分层事实架构

### 3.1 资产职责

| 问题域 | 权威资产 | 内容边界 |
| --- | --- | --- |
| 会话如何开始 | `AGENTS.md`、根 `README.md` | 强制规则、有限阅读顺序、快速入口 |
| 产品目前是什么状态 | `docs/current-state.md` | 验收状态、实现状态、下一步、目标与禁区 |
| 产品应该是什么 | `docs/product-contract.md` | 稳定用户目标、交互原则、范围承诺 |
| 系统如何分层 | `docs/architecture.md` | 模块边界、数据流、Provider 和持久化职责 |
| 代码事实在哪里 | `docs/internal/implementation-inventory.md`、CodeGraph | 代码入口、测试、调用关系、已知缺口 |
| 正在改变什么 | active OpenSpec / Comet change | proposal、design、spec、tasks、验证证据 |
| 过去发生过什么 | archived OpenSpec / Comet、Git、历史原型 | 追溯依据，不参与当前事实裁决 |

任何一份文档都不得同时承担“目标、进度、实现、验收”四种职责。需要引用其他问题域时使用链接和简短摘要，不复制完整结论。

### 3.2 冲突裁决

冲突不使用单一的全局优先级，而按问题域处理：

1. 产品目标冲突：以产品契约为准。
2. 完成度冲突：以当前状态账本及其证据为准。
3. 实际行为冲突：以当前代码和有效测试为准，并把偏差登记到当前状态或实现清单。
4. 技术归属冲突：以架构文档为准；代码越界则登记为架构债务。
5. 调用关系冲突：优先重新同步 CodeGraph，再以源码检索和测试复核。
6. 进行中范围冲突：以当前 active change 的规范和任务为准。

无法裁决时必须写明“待确认”及缺失证据，不允许把推断写成已完成事实。

## 4. 一分钟冷启动协议

`AGENTS.md` 将提供固定且有限的读取顺序：

1. 阅读 `docs/README.md`，理解文档地图和问题域权威。
2. 阅读 `docs/current-state.md`，确认当前状态、下一步和禁止事项。
3. 仅在任务需要时读取 `docs/product-contract.md`、`docs/architecture.md` 或实现清单。
4. 检查是否存在 active OpenSpec / Comet change；存在时恢复该 change，不从聊天摘要重建需求。
5. 修改代码前使用 CodeGraph 查询定义、调用者和影响范围；图谱不可用时再使用 `rg` 和源码证据。

入口明确禁止默认遍历 `docs/product-prototype/`、归档文档和所有历史变更。这样既保留追溯能力，也控制新会话的上下文消耗。

## 5. 当前状态账本

### 5.1 文件结构

`docs/current-state.md` 采用以下固定结构：

1. 最近更新时间与证据截止时间；
2. 状态枚举定义；
3. 关键用户能力表；
4. 当前 active change；
5. 最近下一步；
6. 明确禁区与非目标；
7. 已知事实冲突和待确认事项。

每项关键能力至少包含：

| 字段 | 要求 |
| --- | --- |
| 能力 | 用户可理解的稳定名称 |
| 状态 | 五种枚举之一 |
| 事实说明 | 当前真实情况，不写愿景式宣传 |
| 证据 | 用户验收、测试、代码入口或明确决策的可定位引用 |
| 下一步 | 只在仍需动作时填写 |

### 5.2 状态迁移

允许的主要迁移为：

- `TARGET` → `NEXT`：用户确认进入最近实施范围；
- `NEXT` → `IMPLEMENTED_UNVERIFIED`：代码和相关测试已完成；
- `IMPLEMENTED_UNVERIFIED` → `VERIFIED`：用户完成真实场景验收；
- 任意状态 → `OUT_OF_SCOPE`：用户明确决定当前不做；
- `VERIFIED` → `IMPLEMENTED_UNVERIFIED`：后续改动影响原验收结论，需要重新验证。

没有用户验收证据时不得进入 `VERIFIED`。代码存在不等于产品能力已经验证。

## 6. 文档迁移规则

### 6.1 产品契约

`docs/product-contract.md` 只保留目标用户、核心任务、稳定交互原则、产品边界和明确技术选择。类似“已经支持”“当前完成”等进度式描述迁移到当前状态账本。

### 6.2 架构文档

`docs/architecture.md` 说明 Feature、应用服务、仓储、Provider 和桌面运行时的职责，以及本地项目到 Linux 服务器的关键数据流。目标架构必须明确标为目标，不得冒充现有实现。

### 6.3 实现清单

`docs/internal/implementation-inventory.md` 按用户能力映射以下证据：

- 前端入口组件和状态控制器；
- Tauri command、应用服务与仓储入口；
- CNB、TCR、SSH、Caddy 等 Provider；
- 相关测试；
- 已知未接通入口和架构例外；
- 推荐的 CodeGraph 查询起点。

清单记录代码入口，不复制函数实现。跨层修改完成后必须同步该清单和 CodeGraph。

### 6.4 历史资产

`docs/product-prototype/` 等历史资产保留，但执行两项降级：

- 从 `docs/README.md` 的当前主导航中移除；
- 在目录入口或页面显著位置标明“历史讨论资产，非当前产品或实现依据”。

已有文档中“原型已删除”等与文件系统不一致的表述改为“原型不再作为当前实现依据”。

## 7. OpenSpec、Comet 与 CodeGraph 分工

### 7.1 变更恢复

OpenSpec 保存需求和验收场景，Comet 保存工作流状态、交接和阶段证据。`docs/current-state.md` 只链接 active change 并概括其状态，不复制 proposal、design 或 tasks。

完成变更时：

1. 先完成验证并写回证据；
2. 同步当前状态和受影响的权威文档；
3. 同步 CodeGraph；
4. 再归档 OpenSpec / Comet change。

### 7.2 代码导航

CodeGraph 用于回答“定义在哪里、谁调用它、改动影响谁”。它不决定产品目标，也不决定用户是否已验收。实现清单中的每个关键入口应提供稳定符号名或查询线索，避免新会话仅凭文件名猜测。

若 CodeGraph 不可用或生成时间早于关键代码变更：

1. 明确标记图谱可能过期；
2. 使用 `rg`、源码和测试复核；
3. 在完成门禁前重新同步图谱。

## 8. 维护触发器

| 事件 | 必须同步的资产 |
| --- | --- |
| 用户确认真实验收 | `docs/current-state.md` |
| 功能实现但未验收 | 当前状态、实现清单、相关测试 |
| 产品规则改变 | 产品契约、当前状态、对应 OpenSpec change |
| 架构边界改变 | 架构文档、实现清单、CodeGraph |
| 代码入口改变 | 实现清单、CodeGraph |
| change 准备归档 | 当前状态、受影响权威文档、验证证据 |
| 新增历史原型或研究材料 | 历史标识和非权威导航规则 |

这些触发器写入入口和文档地图，作为后续 AI 的完成检查，而不是依赖维护者记忆。

## 9. 冷启动审计

验证阶段模拟一个没有当前聊天记录的新会话，只提供仓库和 `AGENTS.md`。该会话必须在不遍历历史资产的情况下回答：

1. 哪些关键能力已由用户验收？
2. 哪些能力已实现但尚未验收？
3. 最近下一步是什么？
4. 哪些事项明确禁止或不在范围内？
5. 相关前端、应用服务、仓储、Provider 和测试从哪里进入？

每个答案都必须附仓库内来源。出现以下任一情况即判定失败：

- 需要读取旧聊天或会话摘要；
- 需要遍历全部历史原型；
- 通过文件名猜测代码入口；
- 把 `TARGET` 或 `IMPLEMENTED_UNVERIFIED` 回答成已验证能力；
- 无法指出 active change 或工程禁区。

## 10. 验证与质量门禁

实施完成后依次执行：

1. OpenSpec 结构和规范校验；
2. 当前文档链接、状态枚举和问题域权威一致性检查；
3. `pnpm check:project`；
4. `pnpm check:secrets`；
5. 受影响的文档测试或检查；
6. CodeGraph 同步及关键入口抽查；
7. 冷启动审计。

验证证据写回 change 任务和 `docs/current-state.md`。若项目级门禁因本 change 之外的既有改动失败，必须记录具体失败和归属，不得删除断言或修改无关文件换取通过。

## 11. 实施顺序

1. 建立当前状态账本并以证据分类关键能力。
2. 更新 `AGENTS.md`、根 `README.md` 和 `docs/README.md`，形成固定入口。
3. 收敛产品契约、架构文档和实现清单的职责边界。
4. 修正代码仓库来源、历史原型等已知矛盾。
5. 增加历史资产非权威标识。
6. 同步 OpenSpec / Comet 导航和 CodeGraph 入口说明。
7. 执行全部门禁和冷启动审计。

每一步只修改该职责域需要的文件；现有未提交业务改动不进入本 change 的提交范围。

## 12. 回滚策略

本变更不迁移运行数据，也不改变产品逻辑。出现问题时按本 change 的精确提交回退治理文件即可。回滚不得使用破坏性 Git 命令，也不得影响本 change 之外的工作区改动。

## 13. 完成判定

只有同时满足以下条件，治理才可进入归档：

- 冷启动入口有限、明确且可执行；
- 五种状态互斥使用，关键能力均有证据；
- 产品契约、架构、实现清单和历史资产不再争夺同一事实；
- active change 与代码入口能够从当前资产恢复；
- 项目门禁和冷启动审计有可追溯证据；
- 没有夹带或覆盖本 change 之外的用户改动。
