# ABCDeploy 产品合同

> 对齐日期：2026-07-24。本文只定义 MVP 中用户最终看到和经历的产品，优先于原型、当前实现和历史讨论；不描述当前代码或迁移方案。

## 1. 产品承诺

ABCDeploy 帮助不理解部署概念的用户完成一件事：

> 选择一个项目，选择它要运行的地方，处理系统列出的待办，然后得到一个有依据的运行结果。

用户的完整模型只有：

```text
选择项目  →  选择运行位置  →  处理待办  →  运行/上线  →  查看成功依据
```

项目可以来自电脑里的文件夹或代码仓库地址；运行位置可以是这台电脑或某台 Linux 服务器。

代码读取、构建、制品存储、远程连接、运行和路由都是后台手段，不是用户需要理解的产品结构。

## 2. 核心对象

| 对象                    | 用户理解               | 必须保存的事实                                               |
| ----------------------- | ---------------------- | ------------------------------------------------------------ |
| `ProjectSource`         | 要运行哪个项目         | 来源类型、位置、分支、不可变源码身份、推导名称与可选显示名称 |
| `DeploymentEnvironment` | 项目在哪里运行         | 本机或服务器、已验证连接引用                                 |
| `ActionChecklist`       | 现在还必须由我处理什么 | 所有用户动作、阶段、状态、处理入口和验证结果                 |
| `DeploymentRun`         | 这一次运行/上线        | 固定输入、当前状态、尝试、恢复位置和结果                     |
| `DeploymentEvidence`    | 凭什么相信成功         | 预期值、实际值、检查位置、时间和连续通过次数                 |

页面填写过程中允许存在两个草稿对象：

- `ProjectSourceCandidate`：用户刚选的文件夹或刚输入的仓库地址；
- `EnvironmentCandidate`：用户刚选的本机、已保存服务器或尚在验证的新服务器。

草稿允许表达“格式正确但尚未读通”“服务器地址已填写但身份尚未确认”等中间状态。只有验证通过后才生成稳定的 `ProjectSource` 和 `DeploymentEnvironment`；`DeploymentRun` 只能引用稳定对象。

以下对象继续存在于内部，但不作为 MVP 默认导航：

- `Connection`：仓库、构建服务、制品存储和服务器的可复用授权；
- `Provider`：代码托管、构建、制品存储、服务器和路由的具体实现；
- `Release` / `Artifact`：不可变运行版本和摘要；
- `AccessEndpoint`：某个公开服务的访问地址及其 DNS/TLS/请求证据；
- `DeploymentStage`：任务内部阶段和技术日志。

## 3. 页面结构

### 3.1 我的部署

首页名称统一为 `我的部署`，只提供：

- 已保存的部署列表；
- `新建部署`；
- 打开已有部署。

每条记录的次级菜单允许“移除部署记录”。该操作只清除 ABCDeploy 本机保存的项目级部署状态，不删除源码、不停止或删除服务器上的服务，也不删除可复用连接。远端下线属于以后独立设计的高风险操作。移除后再次选择同一项目必须按新部署开始，不继承旧线路、任务、待办和项目绑定。

MVP 不提供搜索。以后只有记录数量确实造成查找困难时再增加。

一条部署记录表示“一个项目来源 + 一个运行位置”。列表只展示项目名、运行位置、当前真实结果、主访问地址和最近验证时间。首页不增加与这五项无关的一级功能。

首页和部署详情必须读取同一份持久化事实。部署成功后返回首页，列表立即显示这次结果；再次打开该记录时直接恢复最近一次成功依据和地址，不要求重新选择运行位置或重新执行部署。证据超过新鲜度后可以自动复查，但不能把“查看已有结果”变成“重新新建部署”。较新的更新失败不得抹掉仍在线的上次成功版本，列表应同时表达“服务仍在线”和“本次更新未完成”。

首次没有可复用的构建服务或版本仓库连接时，系统在当前主线收集并验证最少授权信息，验证成功后保存为可复用连接。首次接入规则固定为：

- 代码平台只向用户索取最小访问授权。系统选择账号中默认的可写空间，以项目名生成仓库名并幂等创建私有代码仓库；用户不填写仓库路径。
- 版本存储只向用户索取平台真正需要的命名空间、登录用户名和访问密码，固定地址由适配器隐藏。系统建议首次创建可跨项目复用的 `abcdeploy` 命名空间；每个项目的版本仓库由后续推送产生，不要求用户逐个创建。
- 当前版本不额外保存云厂商资源管理密钥，也不冒充能够代替用户开通平台服务或创建平台级空间。缺少这些资源时，当前待办打开准确控制台并给出建议值；用户返回后提交登录信息，继续原任务。
- 平台没有客户端写入接口时采用一次性网页交接：客户端生成仓库名、文件名和内容并打开准确编辑位置，用户只负责创建或粘贴后确认保存。

已有连接有效时自动复用，不重复询问；当前项目缺少普通代码仓库时仍由系统自动补齐。任何外部步骤确认前不得把部署线路标记为已就绪。

列表标题是项目的显示名称，不要求用户在新建部署时额外填写。名称规则固定为：

1. 用户曾主动重命名时，使用自定义显示名称；
2. 本地文件夹默认使用所选根文件夹名称；
3. 代码仓库默认使用仓库路径最后一段，并移除 `.git` 后缀；
4. 只有确实无法取得名称时才回退为 `未命名项目`。

系统不根据项目内容或 AI 推断业务名称，避免多语言项目和 Monorepo 产生歧义。重命名只改变列表展示，不改变源码身份、部署记录身份、访问地址或更新判断；同一项目运行在不同位置时可以显示相同标题，由下方运行位置区分。

### 3.2 新建或编辑部署

同一个自然纵向页面固定展示：

1. 选择项目；
2. 选择运行位置；
3. 自动检查结果和完整待办；
4. 当前唯一主操作、运行过程或结果区域。

选择、待办、运行和结果都留在这一页；技术执行阶段不成为用户需要配置的页面对象，“结果”也不是新的路由或产品层级。

### 3.3 缺少外部资源时的从零引导

用户可能尚未拥有服务器、代码平台账号、版本仓库或域名。系统不能默认这些资源已经存在，也不能只显示平台名称或失败信息。每一种外部资源都必须在实际选择或填写位置提供折叠式的“还没有？查看准备方法”入口；默认收起，不打扰已有资源的用户。

展开后的引导只回答四件事：

1. 这项资源用来做什么；
2. 去哪个官方页面开通或购买；
3. 需要准备哪些最少信息；
4. 完成后回到当前页面点击什么继续。

资料来源优先级固定为：平台官方说明与控制台、可信的非官方说明、ABCDeploy 自行整理的简明步骤。外部链接必须指向具体动作，不链接到含义宽泛的官网首页；Provider 调整能力或字段时必须同时核对引导内容。

MVP 至少覆盖以下四类从零场景：

- 没有服务器：引导购买受支持的 Linux 服务器，准备公网地址和登录凭据，并确认安全组允许当前适配器需要的连接与访问端口；返回后使用“连接新服务器”。
- 没有代码平台服务：引导注册当前适配器支持的平台并创建具备所需范围的访问令牌；系统验证授权后自动创建或补齐当前项目的私有仓库，不让用户自行设计仓库路径。
- 没有版本仓库：引导开通当前适配器支持的个人版本仓库、创建可复用命名空间并取得登录用户名与访问密码；返回后只填写这些最少字段。
- 没有域名：能安全提供临时地址时不阻塞上线；确实需要自有域名时，引导完成域名注册、必要备案和 A 记录解析，再回到当前访问地址表单继续验证。具体域名仍只属于当前部署记录。

用户完成平台外步骤后，系统必须回到同一草稿或同一部署任务进行真实验证，不能因为用户点击“已完成”直接变绿，也不能要求重新选择项目、服务器或重做已经完成的构建。

## 4. 选择项目

### 4.1 本地文件夹

用户通过系统选择器选择项目文件夹。系统自动识别版本信息、服务、启动方式、端口、运行描述和配置声明。

选择时生成可更新的发现快照，用来列待办；点击运行/上线前重新计算内容身份：

- 内容没有变化，直接生成最终不可变快照；
- 内容已经变化，旧检查失效，系统自动重新扫描；
- `DeploymentRun` 只引用重新确认后的最终快照，包含未提交修改。

MVP 默认不向用户源码目录写任何文件。运行配置、生成文件和仓库副本全部进入 ABCDeploy 管理目录；需要兼容旧项目目录写入的能力不属于本轮主线。

### 4.2 代码仓库地址

用户粘贴仓库地址。空值或明显不符合 Git URL 结构时在输入框旁直接提示，尚不形成候选对象。格式有效后系统读取仓库默认分支并锁定具体 Commit：

- 公开仓库自动读取；
- 私有仓库需要授权时形成待办；
- 地址格式有效但无法访问、授权不足或内容不可运行时分别形成待办；
- MVP 不提供分支选择，固定使用仓库默认分支。

仓库来源保存地址、默认分支和 Commit SHA，界面不能只显示“最新代码”。每次再次运行/上线前重新解析默认分支；Commit 有变化时重新检查并生成新的最终源码快照。

仓库拉取到 ABCDeploy 管理的隔离目录，不污染用户已有项目。

## 5. 选择运行位置

### 5.1 这台电脑

本机是正式的一类运行位置：

- 本地文件夹从最终快照运行；
- 仓库项目从管理目录运行；
- 系统自动检查和准备端口、运行工具、依赖、配置与访问地址；
- 主操作为 `在本机运行`；
- 成功结果为 `运行成功`。

### 5.2 Linux 服务器

用户选择已验证服务器，或通过当前服务器适配器连接新服务器。适配器声明连接所需的最小字段、秘密字段、可自动验证的事实和确实需要用户确认的身份信息；页面按声明动态呈现，不在产品合同中固定协议、端口、登录身份或凭据类型。

连接表单不要求项目域名、运行工具和路由配置。显示名称从已经验证的连接事实中生成，连接后可以在次级设置中改名。

解析连接时，适配器必须先验证能够在不产生远端副作用的阶段验证的目标身份、凭据和支持性。只有适配器声明必须由用户判断的目标身份歧义才形成确认待办。验证完成后建立可复用安全连接，立即清除内存中的临时凭据并保存稳定连接。验证通过前不修改服务器，也不能生成稳定 `DeploymentEnvironment`。

保存过的服务器不代表永久有效。每次使用前必须重新验证当前身份和授权：网络暂时不可达时允许重新检查；密码、受管密钥或服务器身份变化时，当前部署内提供唯一的“重新连接服务器”。重连表单复用名称、地址、端口和登录用户，只重新收集必须的临时凭据；服务器身份变化必须先让用户确认，成功后更新稳定连接并自动继续同一轮检查。临时密码不保存、不进入日志，成功、取消或离开页面后立即清除。

具体适配器的系统、架构、权限和网络支持范围由适配器能力声明和自动检查结果决定。超出范围时，系统必须在首次写入前显示“不受当前版本支持”，而不是尝试性接管。

系统自动完成能够安全完成的运行环境、目录和访问路由准备。遇到无法识别的既有服务、资源冲突或无法证明安全的修改时停止，不静默替换。

服务器连接通过后，系统必须独立检查运行环境。受支持的新服务器缺少必要的容器运行与编排能力，或相关服务尚未启动时，系统默认幂等安装、启动并验证，然后自动继续当前部署；用户不需要自行生成密钥或登录服务器执行命令。自动准备失败属于系统失败，必须说明实际原因、已完成事实、是否修改服务器和明确恢复动作，不能显示成不可操作的“能力检查不完整”。

国内服务器的软件来源选择由系统处理：自动识别运行位置，把同位置可信来源排在前面，并以现场连通性和完整性校验作为最终选择依据；候选来源失败时自动降级，不要求用户理解或选择技术来源。系统不得覆盖服务器已有可用配置，也不得把运行工具来源、公共组件来源和项目版本存储混为一体。

主操作为 `上线到服务器`。只有运行证据和全部必要访问证据达到门槛时才显示 `上线成功`。

## 6. 自动检查与完整待办

项目候选和运行位置候选确定后，系统立即并发检查。检查整体状态必须明确保存：

```text
idle → scanning → blocked | ready | check_failed
```

- `scanning`：仍有必需检查器未结束，主按钮不可用；
- `blocked`：检查完成，存在用户待办；
- `ready`：全部必需检查器完成且没有未解决待办；
- `check_failed`：系统检查或自动准备自身失败，不能因为待办数暂时为 0 而亮起按钮。

只有 `ready` 可以开始运行/上线。每轮检查拥有 revision；项目、源码内容、运行位置或相关配置变化后，旧 revision 和证据立即失效。

### 6.1 系统动作与用户待办

准备运行工具、建立可复用连接、创建受管目录、探测端口和准备访问路由等安全自动动作由系统直接执行，只展示检查结果，不要求用户点击。

只有必须由用户输入、授权、选择或在外部平台完成的事情进入 `ActionChecklist`，例如：

- 补充项目声明的必要配置；
- 授权私有代码仓库；
- 确认目标服务器身份；
- 选择系统无法安全决定的端口或公开服务；
- 完成系统不能代办的自有域名解析。

自动动作失败时显示 `系统准备失败`，固定说明发生了什么、已保留什么，并提供 `重试` 和 `查看技术详情`。只有确认必须由用户外部处理时，才转换为用户待办；不能把系统准备步骤伪装成待办按钮。

### 6.2 列表规则

- 一次展示当前 revision 的全部已知用户待办和准确数量；
- 私有仓库授权、服务器身份确认等信息屏障解除后，自动开启新的 revision 并完整重扫；每一轮都一次展示当时能够发现的全部事项，不把已知事项逐项串行解锁；
- 所有待办同时可处理，不使用“等待前项”逐个解锁；
- 每行展示状态、事项、原因和唯一处理动作；
- 行状态只有 `待处理`、`检查中`、`已完成`、`仍有问题`；
- 用户点击“我已完成”不能直接变绿，必须由系统验证；
- 处理后留在原页面，列表自动刷新；
- 待办全部通过只表示检查可以进入 `ready`，不能推导部署成功。

`ActionChecklist.phase` 区分：

- `readiness`：开始前待办；全部完成后允许创建部署任务；
- `verification`：服务已启动后仍缺少的访问或证据动作；完成后只继续验证，不重新构建。

## 7. 访问地址与多服务

访问地址属于当前部署记录中的 `AccessEndpoint`，不属于可复用服务器连接。连接服务器时不要求用户先填写项目域名。

系统扫描服务后区分：

- 必须运行但不公开的内部服务；
- 需要对外访问的公开服务。

项目有多个公开服务时，为每个服务生成独立地址并选出一个主地址；首页展示主地址和“另有 N 个地址”，结果区域展示全部地址。所有必要内部服务必须健康，所有声明为公开的地址必须通过，才可成功。系统无法判断服务是否应公开时才形成选择待办。

成功页的唯一打开动作固定为 `打开网页`，只打开主地址。主地址优先使用项目明确标记的用户界面服务；没有声明时才按稳定规则选择。其他地址仍可逐项打开，但不再出现含义不明的通用 `打开项目`。运行版本默认只展示服务数量和已核验结论，逐服务不可变身份按需展开，不能挤占主要结果和地址。

服务器适配器能够安全提供临时地址时，系统自动准备并验证，具体生成方式不要求用户理解。用户可以在次级操作中换成自有域名；使用自有域名时才生成解析待办，并要求域名与安全访问检查通过。临时地址已经可访问时，不强迫用户先拥有域名。

如果一次真实验证确认某台服务器或其云厂商策略不接受系统生成的临时域名，系统必须把“需要已备案域名”记为该服务器连接的可复用能力事实。后续项目选择同一服务器时，不再生成或尝试临时域名，而是在构建和部署前直接要求为每个公开服务填写可用域名。该能力事实可以跨项目复用，但具体项目域名仍只属于对应部署记录，不得在项目之间自动复制。

访问地址不得通过通用“检查服务器”动作补充。系统已经识别出公开服务但无法自动得到地址时，当前待办直接打开精简地址表单：每个公开服务只对应一个地址字段，优先预填系统生成的临时地址，用户可以确认或替换为自己的域名。保存后只继续访问入口配置和验证，不重复读取源码、构建版本或重启已经正常运行的服务。

## 8. 部署任务

点击主按钮前，系统重新确认源码内容和 readiness revision。任何变化都会返回自动检查，不创建半旧半新的任务。

确认无变化后，系统一次固定：

- 最终源码快照；
- 稳定运行位置；
- 配置引用；
- 公开服务与访问地址计划。

随后创建可恢复的 `DeploymentRun`。运行页面必须持续读取后台已经持久化的任务事实，不能用前端动画或一次性文案模拟进度。默认视图展示当前阶段、已完成/总步骤、已运行时长、最近一次活动时间、是否可以关闭客户端和 `查看部署详情`。超过 30 秒没有新活动时，明确说明系统正在等待远端返回，并再次告知任务和已完成结果都会保留，不能让用户猜测客户端是否卡死。

“生成运行版本”和“保存运行版本”是两个连续但可独立恢复的后台阶段。前者完成表示镜像已经产生，后者完成才表示镜像已进入目标版本仓库。版本仓库拒绝写入时，用户看到的主问题必须是“版本仓库授权无法保存当前项目版本”，主操作为 `更新版本仓库授权`；已生成镜像、源码快照和构建编号全部保留，授权修复后从上传阶段继续。

`查看部署详情` 展示任务编号、构建编号、代码版本、已生成版本数量、当前技术阶段和问题编号；Provider、命令和脱敏日志仅在确有帮助时继续下钻。详情只读，不是可编辑流程。后台任务进入成功、需要处理、失败或取消状态后，前端必须立即停止“正在处理”，展示同一条持久化结果。

任务没有完成时，面向用户的恢复卡必须排在技术详情之前，并固定回答：发生了什么、哪些版本或步骤已经保留、下一步系统会检查什么，以及修复后从哪一步继续。恢复卡只提供一个与问题匹配的主动作；例如通用服务器失败使用 `检查服务器并继续`，必要配置缺失使用 `补全运行配置`，访问地址缺失使用 `设置访问地址`。按钮必须直接进入对应处理或从失败阶段继续，不能只显示问题编号、让用户自行猜测，也不能用没有修复能力的通用 `重试运行` 制造重复失败。

必要配置恢复必须以本次上线实际缺少的用户输入为唯一口径。失败提示、待填数量、默认展示字段和保存门槛必须一致；数据库、缓存、内部随机密钥等已经由系统接管或生成的配置，即使在脱敏后的完整配置文件中显示为空，也不得再次列为用户待办。用户主动查看其他配置时可以展示完整内容，但必须明确它们不会阻塞本次上线。

远端执行输出可能同时包含下载器、容器运行环境和脚本的多行信息。后台必须优先保留经过脱敏的稳定问题码行，再生成用户提示；不得因为最后一行是退出状态或命令噪声而丢失前面已经识别出的真实原因。未知原始命令仍不得直接暴露给用户。

客户端关闭后重开恢复同一任务和事实状态。重试新增 Attempt，不改写历史输入；新版本失败时独立确认旧版本是否仍在运行。

## 9. 成功依据

命令退出正常、构建完成、运行版本生成或内部阶段全部变绿，都不足以证明成功。

### 9.1 证据链

```text
最终源码身份
  → 生成的运行版本或本地运行身份
  → 所选运行位置实际运行的版本/进程
  → 必要服务与依赖健康
  → 每个公开地址的用户视角请求结果
```

每条证据保存检查项、预期值、实际值、检查位置和时间。最终成功要求关键检查连续通过至少 3 次，相邻检查至少间隔 5 秒，总稳定窗口至少 10 秒。

成功结果面向用户显示 `源码版本` 和 `运行版本`：源码版本使用最终 Commit 或快照身份；服务器运行版本按服务展示实际核验的不可变镜像摘要。部署任务编号、构建编号只属于可展开的技术详情，不能作为或冒充运行版本。任一服务缺少有效镜像摘要时，不得显示“当前运行成功”。

成功证据的新鲜度为 5 分钟：

- 5 分钟内可以显示当前成功；
- 超过 5 分钟只能显示 `上次验证通过 · 待复查`，不继续使用绿色“当前正常”；
- 打开已有部署或客户端恢复时自动重新验证；
- 无法联网或连接运行位置时保留历史事实和时间，但不能冒充当前结果。

### 9.2 本机运行证据

至少同时满足：

- 实际运行的是最终源码快照；
- 所有必要进程或容器仍在运行；
- 必要端口真实监听；
- 运行依赖可连接；
- 所有公开本机地址连续检查通过。

### 9.3 服务器上线成功

至少同时满足：

- 源码身份与不可变运行版本可追溯对应；
- 服务器实际运行身份与预期版本一致；
- 所有必要服务和依赖健康；
- 每个访问地址命中正确服务；
- 从服务器外部访问全部公开地址成功；
- 使用自有域名时 DNS、TLS 和证书均通过。

服务已运行但任一必要公网地址未通过时，页面显示 `服务已运行，访问地址仍需处理`。已经生成的版本和运行事实全部保留，问题进入 `verification` 待办，修复后只继续访问验证，不能重复构建。

### 9.4 业务验证边界

MVP 只支持至少包含一个 HTTP 可访问服务的项目。纯 CLI、定时任务和没有 HTTP 入口的后台 worker 明确显示“当前版本暂不支持”，不伪造访问证据。

默认端口和 HTTP 检查只能证明服务运行并可访问。项目声明健康接口或冒烟检查时才额外显示 `业务验证通过`；没有业务探针时，不宣称登录、支付或其他业务功能正常。

## 10. 结果区域

结果区域按顺序展示：

1. `运行成功`、`上线成功` 或明确的非成功状态；
2. 主访问地址及其他公开地址；
3. 部署了哪份代码；
4. 实际运行在哪里、运行什么版本；
5. 服务、依赖和访问证据；
6. 连续验证次数、稳定窗口和最近检查时间；
7. 按需展开的技术详情。

失败或证据不足时固定回答：发生了什么、哪些事实已成立、旧版本是否仍可用、还需处理什么、修复后从哪里继续。

### 10.1 当前在线与更新

已有部署的详情页默认回答三件事：服务器当前运行什么版本、运行在哪里、最近一次验证是否通过。页面只保留一个高频主动作 `更新上线`，不把更新拆成新的部署线路或新的页面。

点击 `更新上线` 后，系统重新读取并锁定当前源码快照，复用该项目与服务器已经保存的部署设置。若源码身份与当前在线版本一致，直接提示“已经是最新版本”，不创建上线任务，也不新增上线记录。若存在新版本，则创建一次新的上线尝试；只有新版本完成服务器部署和外部验证后，才能替换当前在线指针。更新失败必须留下失败记录，但当前在线仍指向上一个验证通过的版本。

同一项目与服务器同一时刻只允许一个会改变线上状态的任务运行。更新、恢复和首次上线共用目标锁，不能只依赖按钮禁用。

### 10.2 上线记录与版本恢复

上线记录的固定维度是 `项目 + 服务器`。每条记录不可变，至少保存操作类型、发生时间、源码身份、逐服务不可变运行身份、目标服务器、公开地址、最终结果和验证证据。首次上线、后续更新、恢复以及失败尝试都追加新记录，不能覆盖历史。

MVP 中上线记录本身就是版本管理，不新增独立“版本管理”页面。只有曾经验证成功且仍可取得不可变运行版本的记录显示 `恢复此版本`。恢复不是修改旧记录，而是使用该记录的运行版本创建一次新的恢复尝试；恢复验证成功后才更新当前在线指针，失败时继续保留原在线版本并追加失败记录。

### 10.3 部署设置

已有服务器部署的结果页通过更多菜单提供低频入口 `部署设置`，用于维护下一次更新会使用的构建服务、版本仓库、运行服务器和访问地址。该入口与首次上线复用同一个配置组件和校验能力，但必须是独立的 `settings` 模式：展示全部当前选择，允许切换已经验证的可复用连接，并在连接失效时进入对应授权处理。

详情页入口副文案固定使用用户任务语言“修改下一次更新使用的部署资源和访问地址”，不得在入口直接罗列具体平台名称。平台名称只在用户打开设置、需要辨认当前连接或处理授权时出现。

从用户心智上，这个抽屉就是首次上线时使用的同一个 `部署设置`，而不是另一套配置页面，也不是重新进入首次上线流程。首次上线负责建立部署线路，部署详情中的入口负责维护这条既有线路；两者读取和写入同一份项目与服务器部署设置。

首次上线使用 `initial` 模式，只展示当前缺少的信息，主动作是 `准备并继续`，保存后回到同一轮上线任务。后续维护使用 `settings` 模式，打开后默认只展示构建服务、版本仓库、运行服务器和访问地址的只读摘要，不直接出现表单或步骤条；摘要正文提供 `修改部署设置`，底部只允许 `关闭`，打开或关闭摘要绝不能保存任何内容。用户明确点击 `修改部署设置` 后，才在同一个抽屉中进入两个连续步骤：第 1 步 `部署资源` 维护构建服务、版本仓库和运行服务器，主动作是 `下一步：确认访问地址`；第 2 步 `访问地址` 维护主要网页和其他公开服务地址，最终动作是 `保存为下次上线设置`。保存后回到只读摘要并提示“将在下一次更新时使用，当前在线版本没有改变”；取消修改则丢弃本次草稿并回到摘要，而不是关闭抽屉。整个过程不创建部署任务、不触发构建、不重启服务、不替换服务器当前运行版本。首页不提供 `部署设置` 入口，避免把低频配置混入日常结果浏览。

两种模式必须是同一个组件、同一份字段定义和同一套校验能力，不能再跳回历史设置页面或维护两套表单。区别只来自进入场景：`initial` 模式隐藏已由系统确认的内容，并明确“保存后继续本次上线”；`settings` 模式显示当前整条线路，并明确“保存不等于上线”。

模式切换不得改变用户正在处理的对象。`initial` 模式始终绑定当前首次上线任务；`settings` 模式始终绑定当前详情页代表的 `项目 + 服务器`。维护模式保存后只返回该部署详情，下一次点击 `更新上线` 时才读取新设置并重新验证。

该组件的产品名称和抽屉标题固定为 `部署设置`，不得再派生出“首次上线配置”“线路设置”等看起来独立的功能名称。入口场景只通过标题上方的简短标签区分：`首次上线` 或 `后续维护`。`initial` 模式只呈现仍缺少的配置卡片，并将项目、服务器、访问地址等已确认信息压缩成一行“系统已准备”摘要；`settings` 模式的默认只读摘要必须完整覆盖构建服务、版本仓库、运行服务器和访问地址，进入编辑后才展示同一套两步结构 `部署资源 → 访问地址`。编辑态不得把四类信息同时铺成一个长表单，只能按两步逐步确认，并允许返回上一步。不得通过跳转页面或复制表单伪装成两个功能。场景说明最多保留一句：首次上线说明“已准备好的内容会自动复用；保存后继续本次上线”，后续维护说明“保存只影响下次更新，当前在线版本不会改变”。

`initial` 模式保存、授权或完成外部交接后，必须为同一上线任务触发一次完整重检：仍有缺项时留在同一配置界面并展示剩余事项，全部就绪后才关闭界面并自动续跑。`settings` 模式保存后只刷新线路摘要，不得调用部署执行用例，也不得改变当前在线版本、当前指针或既有成功证据。

## 11. 授权、复用与安全

- 已验证的仓库授权、服务器和配置自动复用；
- 多个候选无法安全判断时才要求用户选择；
- 新连接验证成功后可以保存，后续部署直接复用；
- 当前部署缺少构建或版本存储连接时，在原待办中一次收集该 Provider 确实需要的最小授权与项目标识；验证成功后把秘密保存到系统密钥库、把可复用连接及项目级非秘密标识写入本地部署设置，并自动回到同一轮检查，不跳转另一套工作流；
- Provider 已开放幂等资源接口时由应用服务自动创建项目所需资源。平台开通、命名空间等只有网页控制台或需要另一套高权限云 API 凭据的操作，保持为明确的一次性外部交接；
- Provider 还要求用户到外部控制台保存运行秘密时，系统生成可复制内容和独立待办，明确说明保存位置与用途；本地授权成功不能冒充该外部步骤已经完成；
- Provider 名称和 scope 只在授权辅助说明或技术详情出现；
- 需要复用的授权秘密只进入系统密钥库，普通记录仅保存秘密引用；一次性连接凭据只存在进程内存，不序列化、不写密钥库，并在建立可复用安全连接后立即清除；
- 不同 Provider 的独立凭据不能包装成“一个令牌全搞定”。

连接集中管理属于设置中的次级能力，不占首页一级导航。

## 12. 数据与业务边界

ABCDeploy 只执行项目明确声明的数据库迁移和健康检查，不自动承诺业务数据安全。只有项目元数据明确声明持久数据或迁移风险时，才生成对应备份/确认待办；不会对所有项目强制询问数据库问题。

数据库备份工具、无损迁移策略和业务数据验收不属于本轮 MVP 自动化承诺，结果区域必须如实说明覆盖边界。

## 13. MVP 范围

本轮验证：

- 本地文件夹 → 这台电脑；
- 代码仓库 → 这台电脑；
- 本地文件夹 → Linux 服务器；
- 代码仓库 → Linux 服务器；
- 并发自动检查、完整用户待办和检查失败；
- 可恢复部署；
- 多服务健康、访问地址和可信成功证据；
- 服务运行但访问失败时只继续验证。

MVP 的用户界面只由“我的部署”列表和单页部署编辑器构成。超出上述四种组合及完整待办、任务恢复、访问验证和成功证据的能力，必须先修改本合同，不能因为当前代码已经存在就自动进入产品。

首版后台只需完成一组可替换的代码读取、构建、不可变版本存储、Linux 服务器和受管路由适配。产品默认不接 AI 服务，也不能依赖 AI 才能判断部署是否成功。
